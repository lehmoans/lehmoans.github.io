FEATURED SOFTWARE PROJECT

AutoFluent.

A modular, configuration-driven Python framework for building reusable ANSYS Fluent simulation workflows across local, mock and HPC environments.

View repository ↗ Back to portfolio

01 · PURPOSE

Turning a CFD workflow into reusable software.

AutoFluent grew from the need to automate repetitive CFD setup and make simulation iteration easier. Instead of encoding one particular geometry or case directly into a script, the framework separates simulation configuration from the code that executes the workflow.

DESIGN GOALS
  • Reusable across different Fluent designs and cases.
  • Configuration-driven rather than dominated by case-specific conditionals.
  • Separate physical/process configuration from execution-environment configuration.
  • Support real Fluent sessions as well as mock execution for development and testing.
  • Provide a path from local development to HPC execution.

02 · ARCHITECTURE

A layered simulation workflow.

ENTRY POINT Simulation

Coordinates the overall workflow and passes configuration into the simulation components.

CONFIGURATION Case

Physical and process settings: geometry, mesh, materials, boundary conditions, solver settings, reports and monitors.

EXECUTION Environment

Where and how the workflow runs: local machine, M3/HPC or mock environment, including installation and resource settings.

WORKFLOW Meshing → Solution → Post-processing

Each stage receives the session and relevant configuration rather than owning the entire simulation lifecycle.

MESHING Meshing layer

Creates or prepares the computational mesh. A mock implementation allows workflow testing without Fluent installed.

SOLVER Fluent solver layer

Owns solver setup and execution logic while consuming case and environment configuration.

OUTPUT Reports & post-processing

Provides a place for monitors, reports, contours and other outputs to be defined from configuration.

03 · CONFIGURATION

Case and environment are deliberately separated.

CASE.YAML

Simulation definition

Describes the model itself: geometry, meshing choices, named zones, materials, boundary conditions, solver settings, reports and monitors. These settings should remain useful when the same case moves between machines.

ENVIRONMENT.YAML

Execution definition

Describes the execution environment: local, M3/HPC or mock operation, ANSYS installation location, available resources and adjustable CPU or memory requirements. 

# case.yaml
geometry:
  file: geom.scdC

meshing:
  enabled: true
  show_gui: false
  file: mesh.msh

# environment.yaml
environment:
  type: local
  ansys_root: <ANSYS installation root>
  cores: <number of cores>
  memory: <memory allocation>

04 · USAGE

One workflow, different execution environments.

01

Define the case

Put physical and simulation settings into the case configuration rather than hard-coding them into the workflow.

02

Select the environment

Choose local, M3/HPC or mock execution and provide the corresponding environment settings.

03

Launch

The environment is responsible for establishing the execution context and providing the session to downstream components.

04

Run the workflow

Progress through meshing, solution and post-processing while each component uses the shared configuration and session.

05

Validate

Use reports, monitors and external reference data to determine whether the numerical result represents the intended physical system.

05 · ENGINEERING DOCUMENTATION

Why the architecture matters.

The objective is not simply to automate clicks in Fluent. The larger goal is to create a simulation framework where the model definition, execution environment and workflow stages remain understandable and independently replaceable.

  • Portability: the same case configuration can target different environments.
  • Testability: mock execution makes workflow logic testable without a full Fluent installation.
  • Maintainability: solver stages remain separated instead of becoming one large procedural script.
  • Scalability: execution settings can adapt from local machines to HPC resources.
  • Reproducibility: important simulation choices are represented explicitly in configuration.
